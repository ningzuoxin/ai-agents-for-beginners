# 第 8 章学习笔记：多智能体设计模式（Multi-Agent Design Patterns）

> 本章目标：搞清楚什么时候该把"一个 agent 干所有事"拆成多 agent 协作，拆了以后真正要解决的是什么问题。
> 核心一句话：**多 agent 之于单 agent，约等于微服务之于单体——按职责边界拆，换来专业化、可扩展、容错；代价是通信、协调、可观测性全都要自己建。拆不拆的判断标准是"是否需要不同角色各自带工具、且结果要协调"。**

---

## 1. 最重要的判断：什么时候拆、什么时候别拆

这一章真正的考点不是"多 agent 有什么好处"，而是**拆分决策**（章节两道测验题考的都是这个）：

**该用多 agent 的信号**（测验 Q1 答案）：

- 任务天然分角色，各角色有自己的工具、权限、审计链路，且**结果必须协调**（如退款流程里的风控/支付/合规）。

**该用单 agent 的信号**（测验 Q2 答案）：

- 一套指令 + 一套工具就能覆盖，无专家交接需求。
- 注意两个易混淆点：
  - "agent 配了多个工具" ≠ 需要多 agent——单 agent 配 10 个工具仍是单 agent；
  - "每小时几千次简单分类" ≠ 需要多 agent——那是吞吐量问题，横向扩实例即可，不是架构问题。

> 拓展：**微服务类比**。单 agent → 单体应用，多 agent → 微服务。拆分逻辑一样：按职责边界拆、独立演进、故障隔离；代价也一样：分布式调试难、通信开销、必须先建可观测性。有过微服务经验的话，这套权衡可以直接迁移过来——包括"别过早拆分"这条教训。

---

## 2. 为什么拆了更好（教程讲的 + 教程没讲的）

教程给的三条：

- **专业化**：单 agent 是"通才"，面对复杂任务会困惑，可能去做自己不擅长的活。
- **可扩展**：加 agent 比往单个 agent 上无限堆工具和指令容易。
- **容错**：一个 agent 挂了，其他继续跑。

> 拓展：**上下文隔离**是教程没讲但很实际的一条技术理由。单 agent 塞下所有工具定义 + 所有指令 → prompt 膨胀、注意力稀释、指令相互冲突，实际表现为"工具越多准确率越降"。拆开后每个 agent 的上下文短而专注，单点准确率反而上升。这和第 15 章"Agent 管动态决策、Actor 管精确执行"是同一个思路：**窄上下文 + 窄职责 = 高可靠**。

> 拓展：**拆分的隐藏成本**也要心里有数——token 消耗 ≈ agent 数 × 各自的对话轮数；串行链路上延迟叠加；错误会级联（上游 agent 输出错了，下游全错），所以链路上要有校验点，别让垃圾结果流到最后。

## 3. 六大构建块：真正难的是前两个

以订行程为例，教程列了六个决策点。实践中难度分布很不均匀：

- **Agent 通信**（难）：决定*谁跟谁共享什么信息*。航班 agent 必须把出行日期传给酒店 agent，否则订错日期。
- **协调机制**（难）：决定*怎么对齐偏好与约束*。用户要"酒店近机场"、约束是"租车只在机场取"→ 酒店 agent 和租车 agent 必须协同满足。
- **Agent 架构**：每个 agent 内部怎么做决策、怎么学习（如航班 agent 用 ML 基于历史偏好推荐）。
- **交互可见性**：怎么追踪 agent 行为（下面单独说）。
- **多 agent 模式**：集中式 / 去中心化 / 混合，选型见第 4 节。
- **人在回路**：定义哪些动作要人类批准（下单/支付前确认；用户点名要 agent 没推荐的东西时）。

> 拓展：通信落地一般两条路——**消息传递**（agent 间直接对话，业界标准化为 **A2A 协议**，本仓库 `requirements.txt` 里的 `a2a-sdk` 就是干这个的，课程第 2 章有介绍）和**共享状态**（blackboard 模式，大家都读写同一块状态存储）。工具层面的共享则走 **MCP**（agent 连工具），别和 A2A（agent 连 agent）搞混。

### 可见性：多 agent 系统的生命线

教程给的三件套：日志监控（谁、做了什么、何时、结果）、可视化（agent 间信息流图，找瓶颈）、性能指标（耗时、吞吐、推荐准确率）。

> 拓展：本质就是**分布式追踪**的思路。一次用户请求跨 N 个 agent，必须有贯穿全链路的 trace，否则出错时根本不知道是哪个 agent 的锅。现成工具：OpenTelemetry、LangSmith、Foundry 的 traces。经验法则：多 agent 系统的可观测性要**第一天就建**，不是出了事再补。

## 4. 协作模式：教程的三种 + 工业界最常用的一种

| 模式                        | 一句话                                    | 适用                                                |
| --------------------------- | ----------------------------------------- | --------------------------------------------------- |
| **Group chat**              | 多 agent 在同一个群里收发消息、互相回应   | 团队协作、头脑风暴式讨论                            |
| **Hand-off**                | 按预定义规则把任务转给下一个 agent        | 客服分流、工作流自动化                              |
| **Collaborative filtering** | 多个不同专长的 agent 各出推荐，综合成结论 | 荐股：行业专家 + 技术分析 + 基本分析三个 agent 协作 |

> 拓展：工业界用得最多的其实是 **Supervisor / Orchestrator-Worker**（教程没单列，但归在"集中式架构"里）——一个 orchestrator 负责拆解任务、分派、汇总，一群专职 agent 干活。微软 **Magentic-One** 就是这个结构（orchestrator + web 浏览、代码执行等专职 agent）。第 14 章 MAF 的 **sequential / concurrent workflow** 就是它在代码里的直接落地：串行 = 固定顺序交接，并发 = 一拆多再汇合。实践中建议：**先从顺序/并发这种确定性工作流起步，跑稳了再上 LLM 动态路由**（supervisor 用模型决定下一步找谁），复杂度和可控性完全不是一个量级。

## 5. 退款场景的方法论：专属 vs 通用

教程这个例子真正值得带走的是拆分方法论，而不是那一串 agent 名单：

- **流程专属 agent**（只服务退款）：Customer / Seller / Payment / Resolution / Compliance。
- **通用 agent**（跨流程复用）：Shipping（退货物流=普通发货）、Feedback、Escalation、Notification、Analytics、Audit、Reporting、Knowledge、Security、Quality。

> 洞察：agent 数量远比直觉多——除了业务主线角色，还有一整套**横向能力**（通知/审计/报告/安全/质量……）应该抽成共享 agent。这就是中台/平台化思维在 agent 世界的翻版：业务竖切，能力横沉。做作业（设计客服系统）时先列业务主线，再过一遍横向能力清单，基本不会漏。

## 6. 踩坑 & 易错点

- **过早拆分**：单 agent 一套指令+工具能搞定就别拆，多 agent 引入的通信/协调成本远超想象（微服务老坑重踩）。
- **把"工具多"当成"该拆"**：见第 1 节，这是测验里专门埋的坑。
- **错误级联无校验**：链式 hand-off 中上游错了下游照单全收，最终输出看似有理有据实则全错。链路中段要加确定性校验。
- **可观测性后补**：多 agent 出错时定位难度是单 agent 的 N 倍，日志/trace 不先铺好，等于闭眼调试。
- **成本失控**：agent 数 × 轮数的 token 消耗很容易失控，尤其 group chat 模式里 agent 互相刷屏。

---

## 7. 选型心法

- **单 agent**：任务线性、一套指令可覆盖 → 别折腾。
- **确定性工作流**（sequential/concurrent）：步骤固定、按代码编排 → 第 14 章的 AgentWorkflow。
- **动态多 agent**（supervisor / hand-off / group chat）：任务需要运行时决策路由、角色专精 → 复杂度最高，确认收益配得上再上。
- 演进路径：单 agent → 指令和工具膨胀到维护不动 → 按职责边界拆第一步。

- **Magentic-One**：微软通用 agent 系统 = 本章 supervisor 模式 + 专职 agent 的完整范例。
- **第 16 章**生产级客服 agent 是这套东西的集大成：角色拆分 + 交接 + 人在回路 + 可观测性 + 评估流水线，本章的每个构建块在那里都有对应物。
