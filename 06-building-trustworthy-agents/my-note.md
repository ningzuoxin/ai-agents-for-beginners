# 第 6 章学习笔记：构建可信的 AI Agent（Building Trustworthy AI Agents）

> 本章目标：从"功能能用"迈到"系统敢用"——掌握安全设计（系统消息框架 + 参数控制）、威胁建模（5 类攻击与缓解）、以及人在回路（事前闸门 + 风险分级 + 审计留痕）。
> 核心一句话：**可信不是模型自带的能力，而是设计出来的系统属性——用系统消息框架把 prompt 工程质量规模化，用威胁模型决定防护点，用"事前闸门 + 风险分级 + 审计日志"把高风险动作关进护栏，而不是等 agent 做完再问一句"你同意吗"。**

---

## 1. 三条腿：安全设计、威胁建模、人在回路

这章把"可信"拆成三件互补的事，别只盯其中一件：

- **Safety（安全/可靠性）**：让 agent 按设计运行——靠**系统消息框架**做可规模化的指令工程（`README` + `06-python-agent-framework.py`）。
- **Understanding Threats（威胁建模）**：先知道会怎么被攻击，才知道防护点设在哪（`README` 威胁清单）。
- **Human-in-the-Loop（人在回路）**：把人类审批接进运行流程，作为最后一道保险（`06-human-in-the-loop.ipynb`）。

> 拓展：**安全 ≠ 安全（safety vs security）**。本章的 "safety" 指"行为符合设计"（防跑偏、防注入、防越权），不是传统信息安全。但两者的核心心法一致：**不要用 prompt 当边界**（呼应第 4 章）——真正的护栏是架构（校验、限流、只读、沙箱、审批）。

---

## 2. 系统消息框架：把 prompt 工程质量规模化

核心思想：**不要手写每条 system prompt，而是让 LLM 帮你写。** 用一个专门的"元系统消息"作为模板，批量生成结构化、可维护的系统提示。四步（`06-python-agent-framework.py` 的 `demo_generate_system_message` → `demo_use_generated_system_message` → `demo_iterate_and_improve`）：

1. **Meta System Message**：告诉 LLM"你是撰写 AI agent 系统提示的专家，收到公司/角色/职责后要产出结构化、详尽、易被 LLM 理解的角色说明"。
2. **Basic Prompt**：一句人话描述角色，如 `You are {role} at {company} that is responsible for {responsibility}.`——这是喂给元提示的"素材"。
3. **交给 LLM 优化**：system=元消息、user=基本提示；可调 `temperature`（随机性，1.0 更有创造性 / 0.0 更确定）、`max_tokens`（限长）、`top_p`（核采样）。
4. **迭代改进**：微调基本提示 → 重新生成 → 对比质量。**几乎不会有一次性写对的 system prompt**，价值就在能持续小步调优。

> 拓展：这本质上是**"用 prompt 生成 prompt"的元编程**——把系统提示从"手写文本"变成"结构化产物"。收益有两个：**可扩展**（同一 meta 模板 + 不同 basic prompt，快速造出多个角色 agent）和**可迭代**（改模板或改基本提示，批量重新生成）。生成出来的提示词可直接作为 Agent 的 `instructions`，验证效果（Demo 2）。

> 拓展（批判性阅读）：`06-python-agent-framework.py` 把原笔记本的 Azure SDK 同步调用改成了 `OpenAIChatCompletionClient.get_response`，`temperature=1.0` 是教程原值——用于"生成"场景（要多样性）。但如果把生成的 system prompt 用于**需要稳定复现的生产 agent**，应调低温度并可考虑缓存结果，否则每次生成的提示都可能不同。

## 3. 威胁建模：5 类威胁与缓解

先列威胁再谈防护（`README` "Understanding Threats"）。注意缓解手段**高度复用**——输入校验、限流、最小权限、数据校验、沙箱/回退，反复出现：

| 威胁 | 攻击方式 | 缓解 |
|---|---|---|
| **Task & Instruction** | 用 prompt/输入操纵，改变 agent 的指令或目标 | 输入校验与过滤器；**限制对话轮数**（这类攻击需要反复交互） |
| **Access to Critical Systems** | 攻击 agent 与敏感系统之间的通信，直接或用 agent 侧信道套情报 | 系统访问**按需授予**（need-only）；通信加密；认证与访问控制 |
| **Resource / Service Overloading** | 借 agent 的高频工具调用打垮下游服务或推高成本 | 限制对单一服务的请求数；限制对话轮数与请求量 |
| **Knowledge Base Poisoning** | 不直接打 agent，而是污染其知识库/数据源，诱导偏见或错误答案 | 定期校验 agent 用到的数据；**数据访问受控、只有可信者可改** |
| **Cascading Errors** | 攻击制造的故障沿 agent 连接的系统传播、扩大、难排查 | 隔离环境运行（如 Docker 容器）；**回退机制 + 重试逻辑**止住扩散 |

> 拓展：这 5 类的**共同根因是"agent 的连接面 = 攻击面"**——agent 接的工具、数据源、下游服务越多，可被利用的入口越多。所以缓解的通用套路就是把第 4 章的"权限最小化"推广到整个系统边界：**能不给的访问就不给，能限的量就限，能隔离的就隔离，能回退的就回退。** 这也解释了为什么第 1 章强调"工具/权限是设计出来的"。

## 4. 人在回路：从"事后批准"升级到"事前闸门 + 风险分级 + 审计"

`README` 的 HITL 示例是**事后批准**——agent 先生成回复，再问用户 `APPROVE / REJECT`。这个流程有硬伤：**LLM 成本已经花了，副作用（发邮件、写库、发帖）可能已经发生了。**

`06-human-in-the-loop.ipynb` 把它升级成生产可用的三个子模式：

**① Pre-action gate（事前闸门）**：在 agent 执行**有副作用的步骤之前**插入闸门——agent 先"提议动作"，闸门决定是否放行，批准后才真正执行。

| 维度 | 事后批准（README 简版） | 事前闸门（notebook） |
|---|---|---|
| 审批时机 | agent 产出结果之后 | 任何副作用执行之前 |
| 被拒时的 LLM 成本 | 已经付了 | 只为"提议"付费，不为"动作"付费 |
| 不可逆副作用 | 可能已发生 | 被阻止 |
| 审计 | 只是 `print` | 一条带时间戳/动作/理由的 JSON 记录 |

**② Risk tiering（风险分级）**：不是每个动作都要人工审批——读公开 API 和发客户邮件分量完全不同，一视同仁只会浪费人的注意力。

| 级别 | 例子 | 审批流 |
|---|---|---|
| `low`（只读） | 查知识库、查航班、抓公开网页 | 自动执行，仅记审计日志 |
| `medium`（廉价变更） | 缓存结果、加计数器、设提醒 | 自动执行，但进入每日批量复核 |
| `high`（对外/不可逆） | 发邮件、扣款、发到公开频道 | **阻塞，等人工批准** |

> 拓展：notebook 的 `classify_risk` 用关键词启发式（先判 high，再判 low，再判 medium），并把**无法识别的一律默认 `medium`**——这是刻意的 fail-safe：只读关键词集必有盲区，让未知动作走批量复核比直接自动执行更安全。生产环境应把它换成学习型分类器或策略引擎。

**③ Audit log + revision loop（审计日志 + 拒绝重规划）**：`print("Response approved.")` 不是审计。每个闸门决策都写成**追加式 JSONL**（每行含 timestamp / action / risk_tier / decision / reason），可 grep、可回放、可挂到事故复盘。闸门返回 `deny` 时，把**拒绝理由回灌**给 agent，让它提出一个规避该问题的**新动作**，而不是简单重试——`run_with_revision` 会带 `max_revisions` 上限，到顶则标注 `max_revisions_reached`。

> 拓展：**三个子模式缺一不可**。只有闸门没有分级 → 审批疲劳，人被淹没（呼应第 3 章"nudge 不要做成 spam"）；只有分级没有审计 → 出事无法复盘、无法追责；只有审计没有重规划 → agent 被拒后卡死或原样重试。合起来才是"可控的自主"。

> 拓展：**HITL 的实现位置决定体验**。notebook 的闸门是围绕"提议动作"的函数；而在框架里，这类逻辑通常放在**工具调用中间件**（围绕每次 function/tool 调用执行）——`README` 末尾列出的对比正是如此：LangChain 包成工具、AutoGen 用 `UserProxyAgent` 角色代表人类、MAF 用 function-invocation middleware。第 14 章会展开 MAF 的中间件；第 18 章则把这类动作做成可审计、可验签的"收据"。

## 5. 踩坑 & 易错点

- **把可信当成"加一段安全提示"**：安全提示是软约束，拦不住任何东西；可信靠的是校验、权限、限流、沙箱、审批这些**架构手段**。
- **只在事后审批**：副作用已发生或成本已付出；高风险动作要设成**事前闸门**。
- **对所有动作一视同仁地审批**：会导致审批疲劳，人反而开始无脑点"通过"；必须做**风险分级**。
- **审计日志写成 `print` 或自由文本**：无法查询、无法回放、无法关联事故；要写成**结构化、追加式**记录。
- **拒绝后让 agent 原样重试**：必须把拒绝理由回灌，且设**重规划上限**，否则死循环烧钱。
- **忽视提示注入的输入面**：外部网页/文档/工具返回都可能携带指令（第 4、15 章同源）；输入校验与"外部内容视为不可信"是前提。
- **系统提示一次写死**：agent 的 system prompt 需要随用例迭代，用元提示框架把它变成可维护的产物。
- **边界的诚实**：`06-human-in-the-loop.ipynb` 明确声明——认证与访问控制、工具调用中间件、多 agent 辩论等**不在此章范围**（分别属第 6 章威胁 2 / 第 14 章 / 第 8 章），别指望一章打通所有安全。

## 6. 应用心法

- **上线前先做威胁清单**：把 5 类威胁对着自己的 agent 过一遍——它接了什么工具/数据源/下游？每类是"有缓解"还是"裸奔"？
- **按副作用分级设闸门**：先给每个工具标注 low/medium/high，再决定"自动 / 批量复核 / 阻塞审批"，而不是逐个写 if-else。
- **一切决策留痕**：任何影响用户或系统的动作，都要有结构化审计记录（这也是第 16 章可观测性、第 18 章可审计性的雏形）。
- **系统提示工程化**：用"元提示 + 基本提示 + 迭代"的框架维护 prompt，而不是散落在代码各处。
- **默认从严**：风险分类拿不准时默认往高档走（notebook 的 unknown → medium 就是这个思路）。
