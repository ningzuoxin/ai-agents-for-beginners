# 第 1 章学习笔记：AI Agent 入门与用例（Intro to AI Agents）

> 本章目标：建立"什么是 agent、它和普通 LLM 应用的本质区别、什么时候该用/不该用"的判断框架。
> 核心一句话：**Agent = 经典的"感知-决策-行动"架构（环境+传感器+执行器）套上 LLM 当大脑，再用工具和记忆把"生成文本"变成"对世界做事"；不确定的开放问题才值得上 agent，确定性任务用 if/else 更好。**

---

## 1. Agent 到底是什么：一句话拆成五件事

教程定义：**让 LLM 真正"做事"的系统——给它工具和知识去影响世界，而不只是回复 prompt。**

拆开是五个要素：
- **系统**：agent 不是一个模型，是一组协作的部件。最小三件套——**环境**（在哪干活，如订票平台）、**传感器**（怎么读环境状态，如查房价余票）、**执行器**（怎么行动，如下单/发确认/取消）。
- **LLM**：大脑。负责理解自然语言、推理上下文、把模糊需求变成具体行动计划。
- **执行动作**：裸 LLM 只输出文本；放进 agent 系统，文本会变成真正执行的步骤（查库、调 API、发消息）。
- **工具**：能干什么取决于开发者接了什么。订票 agent 能搜航班但不能改客户记录——**权限边界是设计出来的，不是模型自带的**。
- **记忆**：短期（当前对话）+ 长期（客户数据库、历史交互），如"记得你偏好靠窗座位"。

> 拓展：**"环境-传感器-执行器"不是为 LLM 发明的**，它来自经典 AI 教科书（Russell & Norvig《AIMA》），agent 概念比 LLM 早几十年（恒温器、游戏 NPC 都是 agent）。LLM 革命改变的是"决策模块"——过去手写规则/训练小模型，现在换成一个通用的自然语言推理引擎。理解这点，就不会把 "agent" 和 "LLM" 混为一谈：**LLM 是零件，agent 是系统**。

> 拓展：把五要素串起来的运行时本质是一个**循环**：感知（读环境/用户输入）→ LLM 决策（输出"该调哪个工具+参数"）→ 行动（代码执行工具）→ 把结果喂回 LLM → 继续下一轮，直到任务完成。这就是后续章节的 Agentic Loop（ReAct 式"推理-行动"循环），第 3 章的设计模式都建立在这个循环上。

## 2. 七种 agent 类型：先分清两个正交维度

教程用订票 agent 举例列了七类。死记名单没意义，关键是看出它们其实在不同维度上：

**维度一：智能程度（从傻到聪明）**
| 类型 | 核心机制 | 例子 |
|---|---|---|
| Simple Reflex | 硬编码规则，无记忆无规划 | 见投诉邮件→转客服，完事 |
| Model-Based Reflex | 维护内部世界模型并更新 | 追踪历史票价，标记突然变贵的航线 |
| Goal-Based | 有目标，逐步推路径 | 从当前位置规划"机票+酒店+租车"全程 |
| Utility-Based | 不只找解，找最优解（权衡取舍） | 在成本 vs 便利之间打分选最高 |
| Learning | 从反馈中变好 | 根据行程后问卷调整后续推荐 |

**维度二：组织形式（怎么组队）**
- **Hierarchical**：上层 agent 拆任务、下层 agent 执行（"取消行程"拆成取消机票/酒店/租车）。
- **Multi-Agent Systems (MAS)**：多个独立 agent 协作（或竞争）——分酒店、机票、娱乐各一个 agent；或多个 agent 竞价抢单。

> 拓展：前五类直接来自经典 AI 分型，后两类**不是更聪明的 agent，而是更多 agent 的组织方式**——智能维度和组织维度是正交的。今天说的 "LLM Agent" 实际上基本都是 **Goal-Based + Learning 的混合体**（LLM 天生会拆解目标，也天生能从对话反馈调整），所以面试/设计中真正要做的组织决策，恰恰是后两类：单 agent 还是分层？要不要多 agent？——这正是第 8 章（多 agent 设计）和第 14 章（MAF 工作流）的主题。

## 3. 什么时候用 agent（以及教程没明说的"什么时候别用"）

**该用的三个信号**（教程）：
- **开放性问题**：解决路径无法预先编程，需要 LLM 动态找路。
- **多步流程**：需要跨多轮调用工具，而非一次查询/一次生成。
- **需要随时间改进**：系统要从用户反馈或环境信号中变聪明。

> 拓展：**反面清单同样重要**，判断力体现在"不用"上——
> - 路径确定的流程（表单校验、固定 ETL、状态机客服）→ 普通代码，确定性、免费、可审计；
> - 一次调用能解决的（翻译、摘要、简单分类）→ 裸 LLM API 调用即可，套 agent 徒增延迟和 token；
> - 错误代价极高且要求可解释的场景 → LLM 的非确定性是负债，先想清楚护栏（这章埋的伏笔在后续 Trustworthy 课程展开）。
> 一句话：**agent 的价值 = 应对"路径不确定性"，你的任务越确定，越不需要 agent。**

## 4. 三层生态：Development → Patterns → Frameworks

教程把这章收在三个词上，它们是整个课程的地 图：

- **Agent Development（开发平台）**：定义 agent *能做什么*（模型、工具、行为）。课程用 **Microsoft Foundry Agent Service**——多厂商模型（OpenAI/Mistral/Llama）、授权数据（如 Tripadvisor）、标准化 **OpenAPI 3.0** 工具定义。
- **Agentic Patterns（模式）**：手工写死每个 prompt 在多步任务中不可行，需要**可复用的 prompt 编排策略**。课程主线就是按最有用的模式组织的（第 3 章系统展开：工具使用、规划、反思、多 agent 等）。
- **Agentic Frameworks（框架）**：现成的模板/工具/基础设施，解决三件事——接工具、**可观测可调试**、多 agent 协作。课程主线框架是 **Microsoft Agent Framework (MAF)**。

> 拓展：三层的分工类比 Web 开发——平台 ≈ 云服务（托管模型/工具注册），模式 ≈ 设计模式（架构层面的知识，不绑定语言），框架 ≈ Spring/Django（把模式工程化）。**模式是框架的地基**：不懂反射/规划/交接这些模式直接学框架 API，只会调不会设计——这是课程"先模式后框架"编排的原因（第 2 章横向对比各框架，第 3 章深入模式）。

## 5. 踩坑 & 易错点

- **把 LLM 当 agent**：LLM 只是决策零件；没有工具、没有循环，它就只是个聊天框。
- **把七种类型当选择题**：现代 LLM agent 是混合体；真正要选的是组织形式（单/分层/多 agent）。
- **"能用 agent" ≠ "该用 agent"**：见第 3 节反面清单——确定性任务上 agent 只会带来成本、延迟和不可复现。
- **忽视权限边界**：工具给多了 = 攻击面变大，"能搜航班不能改记录"这类边界要在设计期定死（安全相关章节会展开）。
- **跳过模式直接学框架**：框架 API 换代很快，模式寿命长得多。

---

## 6. 选型心法

- 裸 LLM 调用：单步、路径确定 → 最便宜最快。
- 单 agent + 工具：开放问题但一个角色能覆盖。
- 分层/多 agent：任务要拆角色、并行、各有专精（第 8 章的拆分决策）。
- 平台/框架选择：原型期轻框架，要生产级可观测和托管就上 Foundry + MAF（第 2、16 章）。
