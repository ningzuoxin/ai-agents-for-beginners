# 第 16 章学习笔记：把 Agent 部署成可规模化运行的生产服务

> 核心一句话：**上生产真正要干的活，80% 在模型之外的"运营骨架"上；模型本身只占一个生产 agent 的约 20%。**

---

## 1. 最该记住的几个点

- **原型 → 生产的本质区别**：核心循环（推理→工具→回答）不变，变的是循环*外面*裹的一切——托管/版本化、身份、状态、失败、成本、质量、信任。
- **无状态才能水平扩容**：进程内存不存 per-user 状态，对话外置到 thread store / memory service，任意实例才能处理任意请求（无需粘滞会话）。
- **成本第一板斧是选对模型大小**：能通过评估门的小模型，几乎总比同样能过门的大模型便宜。路由和缓存是进一步压榨，但基础模型选错影响最大。
- **评估门是发布前提，不是事后补**：新版本不过离线评估阈值就不发；线上可观测再把真实失败喂回测试集，形成闭环（继承 Lesson 10）。
- **人在回路的本质 = 暂停→真人决策→继续**：退款/删号/升级法务这类重动作，agent 提议后执行暂停，人批准或拒绝再继续。框架叫 approval-required 工具。
- **MCP server 当不可信边界**：锁版本、受限身份跑、校验输出、限流、绝不暴露密钥——它和任何第三方依赖一样要被审计。
- **质量金字塔三层**：smoke test（可达且应答？）每次部署跑 → 离线评估（够好发？）发布前跑 → 在线评估（线上咋样？）持续跑。

## 2. 三种部署模式（按控制权换运维面）

| 模式 | 本质 | 什么时候用 |
| --- | --- | --- |
| Client-Hosted | agent 在你进程里，你直连模型 | 要完全控制循环 / 嵌进已有后端 / 自定义中间件 |
| Hosted Agent | agent 注册进 Foundry，托管推理+thread+RBAC | 要持久化、内置可观测、少运维面（需 Foundry） |
| Agent Workflow | 多 agent/工具编成带控制流的图，可暂停恢复 | 单任务跨多个专职 agent / 中途要审批 |

## 3. 规模化四策略

1. **无状态** — 状态外置，水平扩容的前提。
2. **模型路由** — 简单请求走小快模型，真推理才走大模型；路由的前提是有评估证明小模型够用，否则是拍脑袋。
3. **响应缓存** — 重复问题命中缓存直接返回，最便宜的调用是没发出的调用。
4. **并发+背压** — 限并发、指数退避重试、优雅失败（排队响应好过 500）。

## 4. 生命周期闭环

`Create → Version → Evaluate(离线门禁) → Deploy → Observe(在线) → 收集失败 → 改进 → 回到 Create`；老版本 Retire。

## 5. 纯 Python 版映射（详见 `16-python-agent-framework.py`）

原笔记本用 `FoundryChatClient + AzureCliCredential`（需 Azure）。纯 Python 版用 `OpenAIChatCompletionClient` + 任意 OpenAI 兼容后端，免 Azure 本地跑，复现 8 点：工具 / RAG / 记忆 / 路由 / 缓存 / 真人审批 / 评估门 / OTel 可观测。

- **Hosted Agent 部署/版本化属 Foundry 平台能力，本版无法本地复现**；只保留其教学核心（`release()` 模拟"过评估门再发布"开关）。
- **人在回路可真实模拟**：`issue_refund` 超阈值（`REFUND_APPROVAL_THRESHOLD`）时暂停，由 `request_human_approval()` 在工具内做交互式审批（`REFUND_APPROVAL_MODE`：interactive / auto / reject）。
- **核心请求处理器 = 缓存 → 路由 → 追踪(span) → 跑 → 缓存**。
- **评估门**：离线跑测试集算通过率，不过阈值（默认 0.8）不部署。
